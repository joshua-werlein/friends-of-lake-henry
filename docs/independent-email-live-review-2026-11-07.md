# Independent review — November 7, 2026

Decision: **GO for the timing changes with alerts disabled; NO-GO for live email activation as written.** Production actions require the owner's approval. This review examined only the working-tree changes described in `email-alerts-and-live-latency-2026-11-07.md`; existing raffle behavior was used as a regression baseline.

## Required corrections before live email activation

1. **[P1] Persist an immutable delivery envelope before sending.** `src/lib/server/alerts.ts:74` renders recovery time from the current evaluation, while line 83 reuses the same idempotency key. Line 158 also refreshes alert details/problem text before retries. A local mocked probe confirmed that two recovery attempts use the same key with different bodies. Resend rejects a reused key with a different payload (409); an accepted request whose response was lost can therefore stall retries, and retries beyond the provider's 24-hour key retention can duplicate delivery. Additionally, sending precedes `input.save`: a successful send followed by a storage failure loses firstSeenAt/notified state, so the next evaluation can generate a different key and duplicate the alert. Persist incident identity and a frozen envelope before the first send, use the stored resolvedAt for recovery, retain a delivery ledger, and explicitly handle uncertain outcomes and the 24-hour retry boundary. Add accepted-but-timed-out, failed-save, and payload-changing retry tests. Reference: [Resend idempotency](https://resend.com/changelog/idempotency-keys).

2. **[P2] Verify recovery against authoritative post state.** `workers/facebook-photos/alerts.ts:22` selects only the newest 20 unfinished/failed posts. `src/lib/server/alerts.ts:163` interprets any absent signal as recovery. A local ephemeral-D1 probe opened an incident for a failed post, inserted 20 newer fresh queue entries, and received a recovery email while the original post was still failed. Keep discovery bounded, but recheck every active post incident by indexed post ID before closing it; absence from a limited result is unknown, not healthy. Handle the 100-active-incident load limit explicitly as well, so an unloaded incident cannot be recreated and emailed again.

3. **[P2] Suppress or qualify the webhook-delivery heuristic before emailing it.** `workers/facebook-photos/alerts.ts:48` treats two `source='poll'` completions as proof no signed webhook arrived. Existing `enqueuePost` intentionally preserves the first source when a webhook arrives later; a local D1 probe confirmed this. Simply adding a waiting period does not repair the evidence. Record a signed-webhook receipt per post separately from queue ownership/status, allow a delivery grace period, and exclude backfills/admin requeues. Require two distinct eligible announcements with no receipt after that grace. Until supported, keep this alert dry-run-only or add an individual switch and leave it disabled. Wording should say "polling found the last two posts first" rather than assert delivery failure. Expiration from the seven-day sample should close silently, not claim confirmed webhook recovery.

## Release-document corrections and timing limits

- Lines 86–87 of the implementation document overstate November 6's evidence. A selection timestamp one millisecond after a slot boundary does **not** establish which trigger ran: a webhook-triggered poll can finish near a boundary, and a prior poll can also finish later. The 87-second interval remains unexplained. The simulations establish possible mechanisms, not the historical cause. Change "this removes cause (b)" to "this mitigates the modeled transient-backoff mechanism."
- Alert exceptions are contained, and winner processing / the current Live selection and state writes precede alert delivery. However, `coordinator.ts:124` awaits email work inside the serialized alarm. Failed sends can therefore delay the following alarm, especially after a slow Graph check. The generic engine permits three sequential five-second sends; Live currently has at most two simultaneous signal classes. Do not claim alerts can never delay detection. Before activation, isolate delivery from the scheduler or enforce a measured alarm-time budget and test slow/failing sends with a clock that advances.
- Timing fields and event hashes contain no credentials or raw Graph URLs. `graphMs` measures fetch response arrival, not response-body parsing; `pollMs` includes the broader poll. `firstLiveEvidenceAt` records poll start rather than the precise confirmation instant, and `firstSelectedAt` follows the state write. They are useful correlated stage markers, not exact provider-event times or browser-display measurements. Observability remains off, so use a live tail during dry-run validation; durable first-occurrence timestamps survive separately.

## Confirmed protections

- Migration 008 creates only `ops_alert_incidents` and its index, uses D1-compatible SQLite statements, and alters no winner/import/queue table. Local tests applied it successfully. An additional rollback probe preserved an unrelated table. Missing-table handling sends no email and does not stop processing. Leave the additive table in place on application rollback; dropping it loses deduplication history.
- Both deployed-config candidates set `ALERTS_ENABLED=false`, `ALERTS_MODE=test`. Disabled alerts do not evaluate/read/write. Test mode does not invoke Resend; missing credentials also fall back to test. Keys and recipients are secret bindings, rejected as plain vars by preflight. The sender is server-side HTTPS with a five-second abort timeout; logs omit authorization headers, response bodies, recipient lists, and winner names. HTML is escaped. Retry delays are 4/8/16/32/60 minutes for transient failures and six hours for other 4xx, evaluated on the next eligible tick; recovery attempts stop after five failures. Resend Retry-After is not parsed; consider respecting it as an additional delivery safeguard.
- Burst retry preserves the existing rate-limit classification, Retry-After gates, access pauses, out-of-burst backoff, and the three-failure acceleration limit. The signed-webhook immediate alarm and backoff bypass remain functional; rate-limit/Retry-After and pause gates still apply. Graph transport/classification and raffle publication logic are unchanged.
- November 6 correction data/code and third-place presentation are unchanged in the diff. Their targeted regression tests passed. No existing raffle files were refactored.
- Photo and Live Workers retain different names and bindings; no new DO class/migration or RPC-breaking change was introduced. Either can be upgraded while its existing counterpart remains deployed. The photo Worker still depends on the existing Live service for its established read/notify RPCs; independent deployment does not mean independent operation.
- With alerts disabled, added alert storage cost is zero. Enabled photo evaluations add four SELECT statements per eligible tick plus transition/retry writes. LIMIT bounds returned rows, not necessarily scanned rows: existing indexes do not cover all date-order filters, but the November-sized workload is reasonable. Review growth before another season. Live alerting adds no KV I/O, uses a small DO monitor/map, and expires resolved entries after a week when saving. Timeline storage is at most three transition writes per drawing day. Existing state/selection KV writes remain unchanged.
- Leave KV TTL unchanged. Cloudflare now supports a 30-second minimum, but explicitly requires updated Wrangler; this repository's old Miniflare is not compatibility evidence. Verify a current local runtime and an approved isolated preview using the production compatibility date and actual selection/state reads before proposing the change. No preview was deployed during this review. Reference: [Cloudflare change](https://developers.cloudflare.com/changelog/post/2026-01-30-kv-reduced-minimum-cachettl/).
